# Run Unit Tests

## Why this skill exists

Running the full suite (`vendor/bin/phpunit -c dev/tests/unit/phpunit.xml`,
no path filter) used to crash outright, deterministically, partway through
— a real PHP fatal error, not a test failure:

```
PHP Fatal error:  Class Magento\Sales\Api\Data\OrderExtension contains 164 abstract
methods and must therefore be declared abstract or implement the remaining methods
```

**Root cause (confirmed 2026-09-28):** Magento's own test framework
(`Magento\Framework\TestFramework\Unit\Autoloader\ExtensionAttributesGenerator`)
generates an intentionally **empty** stub for any `*Extension` class the
first time it's autoloaded during a test run — by design, per its own
docblock ("For unit tests, these are just empty type definitions"). That's
fine when the matching `*ExtensionInterface` has zero methods. This
project's `Magento\Sales\Api\Data\OrderExtensionInterface` has **164**
methods (dozens of modules — mostly the SAP integrations — declare
`extension_attributes.xml` additions to Sales Order), so PHP itself refuses
the empty stub: a concrete class implementing an interface must implement
every method. This is a hard fatal that **kills the whole PHPUnit process**,
not a catchable per-test failure — nothing after that point in the run ever
executes, and retrying gives the identical crash every time (this is very
likely why running tests was disabled project-wide on 2026-09-24 as "causing
retry loops" — the loop was retrying a deterministic crash, not a flaky one).

The real, correctly-generated version of this class already exists — it's
just generated by a *different* generator, the one `bin/magento
setup:di:compile` uses (`Magento\Framework\Code\Generator\
ExtensionAttributesGenerator`, a different class despite the similar name),
which properly aggregates every module's `extension_attributes.xml` and
writes all 164 real methods. The fix is to make that correct version
available where the test run's lazy generator looks for it, instead of
letting the buggy generator write its own empty stub first.

## One-time environment setup (redo after `di.xml`/`extension_attributes.xml` changes)

```bash
# 1. Compile DI for real — generates the correct class in generated/code/ (~1-2 min)
bin/magento setup:di:compile

# 2. Copy the correctly-generated class into the path the test run's lazy
#    generator checks first, so it never falls back to the empty-stub generator
mkdir -p dev/tests/unit/tmp/generated/code/Magento/Sales/Api/Data
cp generated/code/Magento/Sales/Api/Data/OrderExtension.php \
   dev/tests/unit/tmp/generated/code/Magento/Sales/Api/Data/OrderExtension.php
```

Prefix both with `docker exec php_bunge_magento2.4 sh -c "..."` if running
from outside the PHP container (see this repo's `Makefile`/`CLAUDE.md` for
the container name and convention). Step 2 alone is the actual fix; step 1
just produces the file step 2 copies — if the file step 2 copies from
already exists and is current, step 1 can be skipped.

If a *different* `*Extension` class starts throwing the same "contains N
abstract methods" fatal in the future (a new module added extension
attributes to a different entity), the fix is the same shape: `setup:di:compile`,
then copy that specific generated file into the matching path under
`dev/tests/unit/tmp/generated/code/`. Don't chase this by disabling test
execution again — it's a one-time, mechanical copy, not a flaky problem.

## Running tests

```bash
# Everything (fast once the fatal is fixed — ~1-2 seconds for the whole suite)
vendor/bin/phpunit -c dev/tests/unit/phpunit.xml

# One module (what a dev should run after finishing a subtask, scoped to their own files)
vendor/bin/phpunit -c dev/tests/unit/phpunit.xml app/code/Webjump/<Module>/Test/Unit

# One file
vendor/bin/phpunit -c dev/tests/unit/phpunit.xml app/code/Webjump/<Module>/Test/Unit/Controller/Adminhtml/<Entity>/SaveTest.php

# One test method
vendor/bin/phpunit -c dev/tests/unit/phpunit.xml --filter=testSaveNewEntitySuccess app/code/Webjump/<Module>/Test/Unit/Controller/Adminhtml/<Entity>/SaveTest.php
```

Always pass `-c dev/tests/unit/phpunit.xml` explicitly — there is no
`phpunit.xml`/`phpunit.xml.dist` at the repo root, so a bare `vendor/bin/phpunit`
(e.g. this repo's current `make unit-tests` target) fails to find any tests
at all.

## Known pre-existing baseline (2026-09-28, after the environment fix above)

```
Tests: 1177, Assertions: 2526, Errors: 187, Failures: 11, Warnings: 7, Incomplete: 1
```

This is real, pre-existing debt (PHP 8.3 deprecations, missing
PHPCompatibility sniffs — see `bunge-backend-code-quality`), not something
either role here fixes as a side effect. Use it as a **diff baseline**, not
a target to reach zero:

- **Ran a scoped run (one module/file) and got new errors** in files you
  just wrote or touched → yours to fix, this is exactly what "escritos, não
  executados" was hiding (confirmed in practice on BUN-14079-3/PR #16: 17 of
  28 tests in one subtask's own new files failed on first real execution —
  a mocked method that doesn't exist, a `create()` on a null factory — real
  bugs in the tests themselves, invisible until run).
- **Ran the full suite and the total is meaningfully higher than the
  baseline above**, in files you did *not* touch → likely a real
  regression from something in this branch; name the specific new
  failures (class + method), don't just report "N more than before."
- **Ran the full suite and the total roughly matches the baseline** (your
  own new module's tests aside) → the pre-existing debt is still there,
  unchanged; that's expected, not something to fix here.

## Fixing a failing test — the 5-attempt safety limit

When a task asks you to **fix** a failing test (not just run and report),
work one test method at a time. Every fix is a real edit-then-rerun cycle —
never guess a fix without rerunning that one method
(`--filter=<methodName>`, scoped to its file) to confirm it's actually
green before moving to the next one.

**If the same test method is still red after 5 distinct fix attempts, stop
trying to fix it.** Five real attempts, not five re-runs of the same
unchanged code — each attempt is a genuine change in reasoning (a different
hypothesis for why it fails), not the same edit retried. Continuing past
that point is exactly the retry-loop failure mode this whole skill exists
to avoid.

At attempt 5's limit, mark that one method incomplete instead of leaving it
red or deleting it:

```php
public function testSomethingThatWontCooperate(): void
{
    $this->markTestIncomplete(
        'Tried 5x: mock expects X but subject calls Y — see delivery report.'
    );

    // ... existing test body left in place, for whoever picks this up next
}
```

`markTestIncomplete()` (`\PHPUnit\Framework\Assert::markTestIncomplete()`,
inherited by every `TestCase`) throws immediately, so nothing after that
line executes — put it as the **first line** of the method body once you
give up on it, and leave the rest of the method's code below it untouched
(useful context for whoever revisits it, not dead weight to delete). The
suite then reports it as `I` (Incomplete), a third state distinct from
`Errors`/`Failures` — it does not fail the run and does not silently
disappear either.

**Never mark a whole test file, a whole class, or more than the one
struggling method incomplete** — the limit is per-method, and every other
method in the same file still needs to actually pass or hit its own
5-attempt limit independently.

**In the final report, list every method marked incomplete**, grouped by
module: file, method name, and the one-line reason from the
`markTestIncomplete()` message (what was tried, what the actual-vs-expected
mismatch was). This is what keeps the root task from blocking on one
uncooperative test — the task reports done with a named, bounded gap
instead of staying stuck or silently shipping a still-red test.

## Who runs what, and when

- **Magento Backend Developer**: after finishing a subtask, run the scoped
  command (your module/file, not the full suite) as your own final check
  before marking `done` — this replaces trusting "escritos, não executados"
  blindly and catches broken tests before they reach a report. This is
  **not** a change to the standing "don't run the full suite or chase
  coverage inside a subtask" rule — stay scoped to what you touched, fix
  what's yours, and if a pre-existing failure surfaces outside your files,
  note it and move on rather than fixing it as a drive-by.
- **Tech Lead**: before pushing a card's code (the existing "push the code"
  step), run the full suite once and compare against the baseline above,
  per the rule in the previous section. Report what you found in the same
  place you already report the push (PR body / issue comment) — a plain
  "tests: no new failures vs. baseline" or the specific new failures named.
  This does not reinstate a hard merge gate or a coverage threshold — it's
  a visibility step, the same spirit as the delivery-report contract
  (`projeto-engineering-practices`) already asks of devs for everything else.
