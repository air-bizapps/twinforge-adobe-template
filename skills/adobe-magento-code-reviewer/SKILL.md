# Magento code review

Review by evidence: `magento-verify` first, then this checklist for what it cannot see. Not for
the Tech Lead gate between subtasks (`bunge-subtask-contract` §4), which does not re-review code.

Commands use `$T`, the scripts folder of `adobe-magento-toolbox` (the `T=` line in that skill).

## Rules

- **Verifier first.** A `VERIFY FAIL` item is a blocker exactly as reported (file:line and fix). Don't
  re-review what it covers: missing classes, PHP that doesn't load, XSD, UI Component wiring,
  RequireJS, Web API docblocks, ObjectManager, fixed URLs.
- **Every finding is one line:** severity, `file:line`, the defect, the fix, the source (skill or doc).
- **Severity decides the merge.** Blocker: security hole, data loss, broken page/route/API, VERIFY
  FAIL. Major: wrong behavior in a real case, measurable performance regression. Minor: standards and
  naming. Only blocker and major hold the merge.
- **Prove behavior by running it.** Partial PUT that nulls fields, list returning only ids, form
  without a save button, empty primary key that never inserts: all read fine and pass every static
  check (`adobe-commerce-standards`).
- **Review the diff, not the module.** Problems in lines the change didn't touch (the verifier lists
  them as "Ignorados (preexistentes)") go in a separate note, not as blockers.

## Checklist

1. **Scope.** `git diff --stat` against the base lists only the task's files; nothing in `generated/`,
   `vendor/`, `pub/static/`, `app/etc/env.php`; no credentials or customer data.
2. **Security** (`adobe-magento-security-analyst`). Each admin controller sets its own `ADMIN_RESOURCE`; each
   `webapi.xml` route has a named resource or `self` with the customer id forced; state changes are
   POST; every value printed in a `.phtml` goes through `$escaper`; no SQL built from input; no
   secret in logs; customer data read by id checks the owner.
3. **Request and persistence** (`adobe-commerce-standards`). Partial update merges with `addData`; the
   Save controller reads `getPostValue()` as the form's `dataScope` sends it and nulls an empty
   primary key; REST errors follow the exception-to-status table; `getList()` returns
   `SearchResultsInterface`.
4. **Extension points** (`adobe-commerce-standards`, `adobe-create-plugin`). Plugin, not preference, on
   core and third-party classes; plugin target public, non-final, obtained by DI; `around` only to
   skip or wrap the call; `<sequence>` only for a real load-order need; `di.xml` in the narrowest
   area (`etc/frontend`, `etc/adminhtml`, `etc/graphql`) when the change is area-specific.
5. **Performance** (`adobe-magento-performance-analyst`). No load or repository call inside a loop; paged
   collections; no `cacheable="false"` on a shared layout handle; storefront entities have cache
   identities; heavy dependencies of CLI commands behind a `Proxy`.
6. **Schema and data.** Tables and columns only in `db_schema.xml`, with `db_schema_whitelist.json`
   regenerated by command; data patches idempotent and never edited or renamed after shipping;
   values looked up by name (CMS identifier, config path, attribute code) exist in the database or in
   a patch.
7. **Frontend** (`adobe-magento-frontend-standards`). Logic in a ViewModel; core JS changed by mixin;
   admin grids and forms as in `adobe-magento-ui-component-developer`.
8. **Tests** (`adobe-create-unit-tests`). Plugins, observers, ViewModels and services have tests that
   assert results, not that files or XML nodes exist.
9. **Project patterns.** Apply `bunge-backend-code-quality` or `bunge-frontend-code-quality` for the
   area. They also list known debt; don't report that debt as new.

## Verify

```bash
php "$T/magento-verify.php"                 # VERIFY OK before reviewing anything else
php "$T/magento-smoke.php"                  # DI + webapi routes; verification database only
php "$T/ui-render-check.php"                # changed UI Components; verification database only
grep -rL "ADMIN_RESOURCE" app/code/Vendor/Module/Controller/Adminhtml    # expect no output
bin/magento setup:db-declaration:generate-whitelist --module-name=Vendor_Module   # whitelist unchanged
vendor/bin/phpcs --standard=Magento2 $(git diff --name-only origin/BASE...HEAD -- '*.php' '*.phtml')
```

Use the project's phpcs standard when it has one (`grumphp.yml` or `phpcs.xml`). Don't run the whole
`grumphp`: it also runs the full PHPUnit suite. REST: `curl` the route with and without a token and
compare the status with the table in `adobe-commerce-standards`.

## Pitfalls

- "The diff looks right" → run the route or open the page and save a record.
- ACL "proven" by an `acl.xml` entry → the check that runs is the controller's `ADMIN_RESOURCE` or
  the route's `<resource>`; the declaration alone enforces nothing.
- Tests that only assert structure → ask for a test of the method's result.
